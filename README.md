 
> 이 저장소는 팀 프로젝트를 fork하여, 본인이 담당한 부분을 중심으로 정리한 개인 저장소입니다.
 
작업 인증 및 장소 기반 기록 공유 SNS 서비스입니다.
 
## 담당 역할
 
| 영역 | 내용 |
|---|---|
| **feed** | 피드 조회/상세, 좋아요·북마크, 캐싱 적용 |
| **notice** | 공지사항 CRUD |
| **inquiry** | 문의 CRUD, 이미지 업로드 연동 |
| **admin** | 운영 관리 기능 |
 
## 기술 스택
 
Java, Spring Boot, Spring Security, MySQL, Redis, QueryDSL, Docker, GCP(Storage)
 
## 주요 구현
 
### 커서 기반 페이징 (feed)
`OFFSET` 대신 `id` 기준 커서(keyset pagination)로 다음 페이지를 조회합니다. `size+1`건을 조회해 다음 페이지 존재 여부를 판단함으로써 별도의 `COUNT` 쿼리 없이 페이징을 처리합니다.
 
### N+1 방지
피드 목록에서 좋아요/북마크/작성자 여부를 게시글마다 개별 조회하지 않고, `postIds` 목록으로 한 번에 배치 조회합니다. 연관 엔티티(작성자, 장소)는 `fetchJoin`으로 함께 조회합니다.
 
### Redis 캐싱 — 개인화 응답과 공용 응답의 분리
피드 조회 응답은 로그인 사용자마다 좋아요/북마크 여부가 달라 개인화된 데이터입니다. 이를 그대로 캐싱하면 다른 사용자의 개인화 정보가 노출되는 문제가 생길 수 있어, **비로그인 사용자의 첫 페이지 응답만** 캐싱 대상으로 좁혔습니다.
 
- 캐시 생성: 비로그인 + 첫 페이지 요청 시 응답을 캐싱 (TTL 5분)
- 캐시 무효화: 게시글 생성/수정/삭제 시 즉시 삭제
**측정 결과** (실제 게시글 100건 이상, 운영 환경)
 
| 상태 | 응답시간 |
|---|---|
| 캐시 MISS (게시글 변경 직후, DB 재조회) | 약 300~370ms |
| 캐시 HIT | 약 50~70ms |
 
약 5~6배 응답시간 개선을 확인했습니다.
 
> 향후 개선 방향: 현재는 캐시 삭제가 트랜잭션 커밋 이전에 실행되어 이론적으로 레이스 컨디션이 발생할 수 있음을 인지하고 있으며, `AFTER_COMMIT` 이벤트 기반으로 개선할 계획입니다. 또한 로그인 사용자까지 캐싱 범위를 넓히려면 게시글 콘텐츠와 좋아요/북마크 등 개인화 상태를 분리해 콘텐츠만 캐싱하는 구조가 필요합니다.
